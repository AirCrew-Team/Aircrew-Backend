# ADR 001: Selección de Estilo Arquitectónico

- **Estado:** Aceptado
- **Fecha:** 10 de octubre de 2026
- **Autores:** Samuel Arredondo Ospina

## 1. Contexto

AirCrew es una plataforma para gestionar vuelos, aeronaves y tripulaciones que, cuando un tripulante falta de forma imprevista, genera una recomendación de reemplazo. Debe atender a cuatro perfiles: supervisores y coordinadores, tripulantes, centro de control de operaciones y administradores.

El backend tiene responsabilidades claramente distintas: vuelos, tripulación, recomendación, notificaciones, y administración de usuarios y parámetros.

Varias condiciones del proyecto influyen en la decisión:

- La carga es irregular: un día normal genera dos ausencias, pero una tormenta puede generar decenas al mismo tiempo (escenario de calidad 1).
- La falla de un módulo no debe interrumpir el funcionamiento de los demás, como pide uno de los objetivos específicos.
- Las reglas y los proveedores cambian: una ley puede modificar el descanso mínimo (escenario 7) o la aerolínea puede cambiar de proveedor de mensajería (escenario 8). Esos cambios deben quedar contenidos en una sola parte del sistema.
- La tecnología del backend es Node.js con Express y PostgreSQL, en un monorepo con npm workspaces.
- El frontend web debe conectarse al backend.
- El plazo objetivo del producto mínimo viable es finales de noviembre, y gran parte del backend la desarrolla una sola persona.

## 2. Decisión

El backend de AirCrew usará una arquitectura de microservicios, con seis servicios dentro de un mismo monorepo: `gateway`, `flights`, `crew`, `recommendation`, `notification` y `admin`.

Cada servicio tendrá su propio código y su propio proceso. Los servicios de negocio tendrán además su propia base de datos (`flights_db`, `crew_db`, `recommendation_db`, `notification_db` y `admin_db`), dentro de una misma instancia de PostgreSQL. Ningún servicio consulta directamente la base de datos de otro.

El frontend se comunicará únicamente con el API Gateway, que recibe las peticiones y las reenvía al servicio correspondiente, sin lógica de negocio.

Dentro de cada servicio se usará una arquitectura en capas: ruta, middlewares, controlador, servicio y modelo.

El código de infraestructura común (manejo de errores, trazabilidad por `correlationId` y cliente HTTP) estará en la carpeta `shared`, que no contiene lógica de negocio.

La forma en que los servicios se comunican entre sí se define en el ADR 002.

## 3. Alternativas consideradas

Se compararon los estilos arquitectónicos estudiados en la materia:

- **Cliente-servidor con un solo servidor:** el cliente (el navegador) inicia una petición y un único servidor procesa toda la lógica y entrega la respuesta. La relación entre el frontend y el backend de AirCrew sigue siendo cliente-servidor, pero se descartó tener un solo servidor porque concentraría toda la lógica en un mismo lugar, sin separar las responsabilidades de vuelos, tripulación, recomendación, notificaciones y administración.
- **Monolito modular (por ejemplo, una aplicación Express organizada con MVC):** el código se organiza en módulos, pero todo se despliega en un mismo paquete. Sería más simple de montar para un equipo pequeño y un plazo corto, pero se descartó por dos razones. La escalabilidad es ineficiente: si un módulo como el de recomendación se satura, hay que escalar toda la aplicación y se gasta memoria en módulos que no lo necesitan. Y hay riesgo de despliegue: un error en un módulo, como el de notificaciones, puede tumbar el sistema completo, incluido el de vuelos.

Se eligen los microservicios porque aíslan las fallas, los cambios y el escalado de cada servicio, a cambio de tener más piezas que montar y configurar, un costo que el equipo asume.

## 4. Justificación

- **Responsabilidades distintas:** vuelos, tripulación, recomendación, notificaciones y administración tienen sus propios datos y sus propias reglas, por lo que se separan de forma natural en servicios independientes, cada uno con su propia base de datos.
- **Despliegue independiente:** se puede actualizar un servicio, por ejemplo el de recomendación, sin desconectar a los demás.
- **Fallos aislados:** si falla un servicio, como el de notificaciones, los demás siguen funcionando; solo falla la operación que depende de él.
- **Escalado por servicio:** si un servicio se satura, como el de recomendación durante una tormenta, se escala solo ese servicio y no toda la aplicación.
- **Cambios contenidos:** cambiar de proveedor de mensajería solo afecta a notification (escenario 8), y el descanso mínimo es un parámetro de admin, así que una ley nueva no obliga a modificar recommendation (escenario 7).
- **Construcción por etapas:** al ser independientes, los servicios se pueden construir uno a uno y probar por separado, y el avance no depende de tener todos terminados al mismo tiempo.
- **Entrada única para el frontend:** el frontend conoce una sola dirección, la del gateway, lo que simplifica la conexión entre frontend y backend.
- **Estructura repetida e infraestructura reutilizada:** al usar las mismas capas en los seis servicios es fácil ubicar dónde va cada pieza de código, y `shared` evita repetir el manejo de errores, el `correlationId` y el cliente HTTP en cada servicio, algo importante cuando gran parte del backend la desarrolla una sola persona.
- Además, la decisión no exige tecnologías nuevas: todos los servicios usan Node.js, Express, PostgreSQL y npm workspaces, que el equipo ya maneja.

## 5. Consecuencias

**Ventajas:**

- Cada responsabilidad queda separada y se puede construir, probar, actualizar y escalar sin tocar las demás.
- Un fallo en un servicio no tumba a los demás; solo falla la operación que depende de él.
- El frontend se conecta a una sola dirección, la del gateway.
- Todos los servicios comparten la misma estructura interna, lo que facilita ubicar el código.
- La infraestructura común se escribe una sola vez y la usan todos los servicios.

**Desventajas:**

- Hay más piezas que montar, configurar y depurar (seis procesos y seis configuraciones) para un equipo muy pequeño.
- Cada servicio tiene su propia base de datos, por lo que no hay consultas cruzadas: si un servicio necesita datos de otro, debe pedírselos por HTTP.
- La carpeta `shared` puede acoplar los servicios si se le agrega lógica de negocio, por lo que debe contener solo infraestructura.
- Todas las peticiones del frontend pasan por el gateway; si este falla, el frontend no puede llegar al backend.
