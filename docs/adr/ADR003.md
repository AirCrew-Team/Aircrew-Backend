# ADR 003: Selección de arquitectura de microservicios

- **Estado:** Aceptado
- **Fecha:** 14 de octubre de 2026
- **Autores:** Samuel Arredondo Ospina

## 1. Contexto

AirCrew debe gestionar vuelos, aeronaves, tripulaciones, ausencias, recomendaciones de reemplazo, notificaciones y administración. Estas responsabilidades pertenecen a áreas funcionales diferentes y pueden crecer o cambiar por motivos distintos.

El proyecto necesita organizar el backend para que sus áreas puedan desarrollarse por separado. El equipo también debe considerar el plazo del producto mínimo viable y el costo de operar varias aplicaciones.

## 2. Decisión

El backend se organizará como una arquitectura de microservicios dentro del repositorio del backend. Cada servicio tendrá su propio paquete, proceso, configuración y responsabilidad. La estructura interna de los servicios de negocio seguirá el patrón hexagonal descrito en el ADR 004.

Se crearán estos servicios:

- **`gateway`:** punto de entrada del frontend. Recibe las solicitudes y las dirige al servicio correspondiente, sin lógica de negocio.
- **`flights`:** vuelos, aeronaves y aeropuertos.
- **`crew`:** tripulantes, ausencias y asignaciones.
- **`recommendation`:** reglas y casos de uso para recomendar reemplazos.
- **`notification`:** preparación y envío de notificaciones.
- **`admin`:** administración de usuarios y parámetros.

El frontend utilizará el API Gateway como entrada al backend. Cada servicio de negocio será dueño de sus datos y no consultará directamente la base de datos de otro servicio.

## 3. Alternativas consideradas

- **Monolito en capas:** todos los módulos se ejecutan como una sola aplicación y se organizan por capas técnicas. Es una opción más sencilla de desplegar al inicio, pero reúne en un mismo proceso responsabilidades que tienen cambios y necesidades diferentes.
- **Monolito modular:** mantiene una sola aplicación y un solo despliegue, pero separa el código en módulos funcionales. Es una alternativa válida para equipos pequeños; sin embargo, no ofrece despliegues independientes para cada módulo y requiere mantener límites estrictos dentro del mismo proceso.
- **Microservicios:** separa las áreas funcionales en procesos y paquetes propios. Aumenta el trabajo de configuración y operación, pero permite que cada servicio se desarrolle y evolucione con una frontera más clara.

## 4. Justificación

- **Responsabilidades diferenciadas:** vuelos, tripulación, recomendación, notificaciones y administración tienen propósitos distintos y pueden organizarse como servicios con límites claros.
- **Cambios localizados:** una modificación de reglas de recomendación puede concentrarse en `recommendation`; los cambios de administración pueden concentrarse en `admin`.
- **Desarrollo por etapas:** se puede avanzar servicio por servicio y mantener en cada paquete las rutas, los casos de uso y los adaptadores de esa responsabilidad.
- **Escalado independiente como posibilidad futura:** si una capacidad requiere más recursos, podrá desplegarse y escalarse por separado cuando exista infraestructura para hacerlo.
- **Aislamiento con límites explícitos:** los procesos separados reducen el acoplamiento de despliegue. La continuidad ante fallos no es automática; dependerá de cómo se gestionen los errores y las llamadas entre servicios.
- **Punto de entrada único:** el API Gateway evita que el frontend tenga que conocer las direcciones internas de cada servicio, una vez que el enrutamiento esté implementado.

Se acepta el costo de configurar y mantener más procesos porque la separación por responsabilidades es una decisión central del backend de AirCrew. La implementación se hará gradualmente, sin agregar lógica de negocio antes de que cada servicio se trabaje.

## 5. Estructura de carpetas de los servicios

Cada servicio tendrá su propio `package.json` y `.env.example`. Los servicios de negocio usarán una estructura hexagonal común:

```text
services/<servicio>/
  package.json
  .env.example
  src/
    domain/
      entities/
      value-objects/
      services/
      rules/                    # cuando el servicio tenga reglas de dominio
    application/
      use-cases/
      ports/
        inbound/
        outbound/
    adapters/
      inbound/
        http/
          routes/
          controllers/
          middlewares/
      outbound/
        clients/
        persistence/
          models/
          repositories/
    config/
    app.js
    server.js
```

- **`domain/`:** conceptos, entidades y reglas propias de la responsabilidad del servicio. No depende de Express ni de PostgreSQL.
- **`application/use-cases/`:** acciones que coordina el servicio, por ejemplo reportar una ausencia o consultar vuelos.
- **`application/ports/`:** contratos que permiten invocar casos de uso y declarar las dependencias que necesitan, como persistencia o acceso a otro servicio.
- **`adapters/inbound/http/`:** rutas, controladores y middlewares que reciben las solicitudes HTTP y las traducen a operaciones de aplicación.
- **`adapters/outbound/clients/`:** clientes que se comunican con otros servicios por HTTP.
- **`adapters/outbound/persistence/`:** modelos y repositorios concretos para guardar o consultar los datos propios del servicio.
- **`config/`, `app.js` y `server.js`:** configuración del proceso, composición de la aplicación y arranque del servidor.

El gateway tiene una estructura reducida porque no contiene dominio de negocio:

```text
services/gateway/
  package.json
  .env.example
  src/
    adapters/
      inbound/http/
      outbound/http/
    config/
    server.js
```

## 6. Consecuencias

**Ventajas:**

- Las responsabilidades funcionales quedan agrupadas por servicio.
- Los servicios pueden desarrollarse y modificarse por etapas.
- La estructura interna común facilita encontrar casos de uso, reglas y conexiones técnicas.
- El diseño permite despliegues y escalado independientes cuando la infraestructura futura los soporte.

**Costos y riesgos:**

- Hay más procesos, configuraciones y contratos que mantener que en un monolito.
- Las llamadas entre servicios pueden fallar o agregar latencia; deben manejarse con errores claros y límites de espera.
- Separar procesos no garantiza por sí solo que un fallo nunca afecte otras operaciones.
- Las carpetas vacías son una guía de organización y no significan que esos casos de uso o adaptadores ya estén implementados.
