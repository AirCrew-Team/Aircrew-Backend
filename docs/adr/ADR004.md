# ADR 004: Repositorios del proyecto y arquitectura hexagonal del backend

- **Estado:** Aceptado
- **Fecha:** 14 de octubre de 2026
- **Autores:** Samuel Arredondo Ospina

## 1. Contexto

AirCrew mantiene el frontend y el backend en repositorios separados. El backend contiene los microservicios `gateway`, `flights`, `crew`, `recommendation`, `notification` y `admin`, agrupados en un monorepo Node.js con npm workspaces. Por tanto, el proyecto se divide en varios repositorios, mientras que el repositorio del backend agrupa sus servicios.

El backend se está organizando con arquitectura hexagonal. Esta decisión responde también a un objetivo de aprendizaje: como estudiante, resulta interesante aplicar puertos y adaptadores y comprender cómo se integran con los microservicios y el API Gateway.

## 2. Decisión

Se mantendrán repositorios separados para frontend y backend. El frontend consumirá el backend a través del API Gateway; el contrato HTTP entre ambos deberá coordinarse entre los repositorios.

Dentro de cada servicio de negocio se organizará el código con arquitectura hexagonal: el dominio y los casos de uso estarán en el centro, y los adaptadores conectarán ese núcleo con HTTP, persistencia y otros servicios. Las dependencias de código apuntarán hacia el centro: el dominio no dependerá de Express, PostgreSQL ni de otros detalles de infraestructura.

El gateway tendrá una estructura más pequeña, con adaptadores HTTP de entrada y salida, porque su responsabilidad es recibir y dirigir solicitudes y no contiene reglas de negocio propias. `shared` se reservará para infraestructura técnica reutilizable, no para lógica de negocio.

## 3. Alternativas consideradas

- **Un solo repositorio para frontend y backend:** simplificaría algunos cambios coordinados, pero mezclaría dos aplicaciones con ciclos de trabajo y dependencias diferentes.
- **Un repositorio por microservicio:** aislaría por completo los cambios y despliegues, pero aumentaría la gestión de repositorios para un equipo pequeño. Se mantiene un solo repositorio backend con workspaces para los seis servicios.
- **Arquitectura en capas tradicional:** organiza el código por tipo técnico, como rutas, controladores, servicios y modelos. Es más familiar y puede ser más directa al inicio, pero puede hacer que los casos de uso dependan de Express o de la persistencia si no se controlan las dependencias.
- **Arquitectura hexagonal:** separa el dominio y los casos de uso de los mecanismos de entrada y salida mediante puertos y adaptadores. Se elige para aprender y aplicar esa separación en el backend de AirCrew.

## 4. Justificación

- **Separación de repositorios:** frontend y backend pueden tener sus propias dependencias, estructura, historial de cambios y flujo de trabajo, conservando la coordinación mediante sus contratos HTTP.
- **Backend agrupado como monorepo:** npm workspaces permite instalar dependencias y ejecutar cada servicio desde la raíz, mientras mantiene paquetes y procesos independientes por servicio.
- **Aprendizaje:** aplicar arquitectura hexagonal permite practicar conceptos vistos en clase y comprender cómo aislar la lógica del negocio de las tecnologías usadas alrededor.
- **Compatibilidad de patrones:** microservicios definen cómo se divide el sistema en servicios; el API Gateway define la entrada del frontend; y hexagonal define cómo se organiza internamente cada servicio. Se pueden usar juntos porque resuelven problemas distintos.
- **Orden de las carpetas:** `domain/` contiene reglas y conceptos del negocio; `application/` contiene casos de uso y puertos; `adapters/` implementa la entrada HTTP y las salidas a persistencia u otros servicios. `config/`, `app.js` y `server.js` preparan y arrancan cada proceso.
- **Infraestructura común acotada:** `shared/` evita duplicar mecanismos técnicos comunes, como el manejo de errores, sin convertirlo en un lugar para reglas de negocio compartidas.

## 5. Estructura de carpetas

Cada servicio de negocio tendrá la siguiente estructura base:

```text
services/<servicio>/
  package.json
  .env.example
  src/
    domain/
      entities/
      value-objects/
      services/
      rules/                    # cuando aplique, por ejemplo recommendation
    application/
      use-cases/
      ports/
        inbound/
        outbound/
    adapters/
      inbound/
        http/
          routes/
          controllers/
          middlewares/
      outbound/
        clients/
        persistence/
          models/
          repositories/
    config/
    app.js
    server.js
```

- **`domain/entities/`:** entidades e identidad del negocio, sin dependencias de infraestructura.
- **`domain/value-objects/`:** valores del dominio que se validan y usan como conceptos propios del negocio.
- **`domain/services/` y `domain/rules/`:** reglas de negocio que no pertenecen a una sola entidad.
- **`application/use-cases/`:** acciones que ofrece el servicio y coordinación del dominio.
- **`application/ports/inbound/`:** contratos de entrada para invocar casos de uso cuando hagan falta interfaces explícitas.
- **`application/ports/outbound/`:** contratos de lo que los casos de uso necesitan del exterior, como persistencia o notificaciones.
- **`adapters/inbound/http/`:** rutas, controladores y middlewares que traducen solicitudes HTTP a llamadas de aplicación.
- **`adapters/outbound/clients/`:** clientes para solicitar información a otros servicios por HTTP.
- **`adapters/outbound/persistence/`:** implementaciones concretas de persistencia, modelos y repositorios.
- **`config/`, `app.js` y `server.js`:** configuración, composición de Express e inicio del proceso.

El gateway, por no tener dominio de negocio propio, conserva una estructura reducida:

```text
services/gateway/src/
  adapters/
    inbound/http/
    outbound/http/
  config/
  server.js
```

## 6. Consecuencias

**Ventajas:**

- El frontend y el backend pueden evolucionar en repositorios separados.
- Los casos de uso pueden probarse sin iniciar Express ni conectarse directamente a PostgreSQL.
- Se puede cambiar un adaptador, como el mecanismo de persistencia, sin trasladar esa dependencia al dominio.
- La estructura hace visible dónde ubicar reglas, casos de uso y conexiones técnicas.
- Se practica la integración de microservicios, API Gateway y arquitectura hexagonal como parte del aprendizaje del proyecto.

**Costos y riesgos:**

- Hexagonal agrega conceptos y carpetas que requieren disciplina; una estructura extensa sin casos de uso reales puede convertirse en sobrecarga.
- El equipo debe coordinar los contratos HTTP entre los repositorios del frontend y del backend.
- La separación de carpetas por sí sola no garantiza independencia: hay que mantener las dependencias dirigidas hacia el dominio y evitar que `shared` acumule lógica de negocio.
- La estructura se incorporará gradualmente; las carpetas vacías representan espacios para trabajo futuro, no funcionalidades ya implementadas.
