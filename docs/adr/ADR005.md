# ADR 005: Estrategia de Comunicación

- **Estado:** Aceptado
- **Fecha:** 28 de octubre de 2026
- **Autores:** Samuel Arredondo Ospina, Asley Torres y Johan Taborda

### Contexto

AirCrew requiere comunicación entre el frontend y el backend para consultar
información y ejecutar operaciones. Además, cuando un tripulante reporta una
ausencia, el supervisor debe recibir una alerta en tiempo real si está
conectado. Se necesita definir cómo se realizan estas comunicaciones y cómo
se describen sus contratos.

### Decisión

Se adopta un enfoque híbrido:

- **Síncrono:** REST sobre HTTP para solicitudes que necesitan una respuesta,
  por ejemplo, consultas, autenticación y reportes de ausencia.
- **Asíncrono:** WebSocket para enviar alertas de ausencia en tiempo real al
  supervisor conectado, sin consultar repetidamente la API.

La respuesta al reporte confirma que el backend procesó la solicitud; no
confirma que el supervisor haya recibido o leído la alerta. La entrega por
WebSocket requiere una conexión activa. Si se pierde Internet o la sesión,
la alerta puede retrasarse. WebSocket por sí solo no garantiza su recepción.

### Tecnologías consideradas

| Tecnología | Decisión y uso |
|---|---|
| **REST** | Seleccionado para operaciones de solicitud y respuesta entre frontend y backend. |
| **WebSocket** | Seleccionado para las alertas de ausencia en tiempo real a supervisores conectados. |
| **SOAP** | No seleccionado: XML y su configuración añaden complejidad que no se requiere actualmente. |
| **GraphQL** | No seleccionado: no se necesita por ahora la flexibilidad de consultas ni la gestión adicional de esquemas. |
| **gRPC** | No seleccionado: no hay una necesidad actual de RPC de alto rendimiento que justifique su tooling. |
| **Webhook** | No seleccionado para el navegador; puede evaluarse para enviar eventos a sistemas externos. |

### Contratos de comunicación

- Las APIs REST se documentarán con **OpenAPI**, incluyendo rutas, métodos,
  parámetros, respuestas, errores y requisitos de autenticación.
- Los eventos WebSocket se describirán con **AsyncAPI** o un contrato
  equivalente que especifique canal, evento, datos y destinatarios.

### Buenas prácticas

- Las conexiones WebSocket deben autenticar al usuario y autorizar qué
  supervisor puede recibir cada notificación.
- Los eventos deben tener identificadores únicos y manejar posibles
  duplicados. Los errores y las desconexiones deben tratarse explícitamente.
- Debe distinguirse entre el reporte guardado, el evento recibido y la alerta
  reconocida por el supervisor.
- Las entradas de las APIs deben validarse y los endpoints deben usar
  respuestas y códigos de error consistentes.
- No se deben incluir contraseñas, tokens ni otros secretos en logs o
  respuestas.

### Consecuencias y estado actual

REST facilita las operaciones habituales de la aplicación y WebSocket permite
mostrar avisos sin polling cuando el supervisor está conectado. A cambio,
WebSocket requiere gestionar autenticación, permisos y reconexiones.

La comunicación WebSocket para ausencias, el reporte de punta a punta, la
persistencia de notificaciones y los acuses aún están pendientes de
implementación. OpenAPI y AsyncAPI se proponen como contratos; no se afirma
que ya estén creados o verificados.
